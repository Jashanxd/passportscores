# Real visa data with weekly auto-refresh

Today every "visa-free / visa-on-arrival" list is generated by a formula from each country's totals — that is why India currently shows China as visa-on-arrival. This plan replaces the synthetic matrix with real provider data stored in the backend and refreshed weekly.

## What changes for you

- Every country pair reflects the provider's actual rule (India → China becomes "visa required").
- Rankings, regional ranks, access counts and year-over-year deltas are all derived from the stored data instead of hardcoded numbers.
- A "Data updated <date> · source <provider>" line appears in the footer and on the methodology page.
- Data refreshes automatically once a week; nothing in the UI needs a rebuild for data to change.

A paid visa-data provider account and its API key. Good fits:

- RapidAPI "Visa Requirements" / Travel-Buddy style endpoints — cheapest, returns per-nationality destination rules.
- Passport Index / Henley commercial data feed — authoritative rankings plus the full matrix.

Tell me which one you sign up for and I will add the key as a backend secret (never in the frontend) and write the adapter for that provider's response shape. If you want, I can start with the ingestion pipeline and a real curated snapshot so the site is already accurate, then plug the key in when you have it.

## Build steps

1. Enable the backend (database + scheduled jobs).
2. Create tables: `countries`, `visa_rules` (nationality, destination, access kind), `passport_snapshots` (per-country weekly rank/counts), and `data_sync_runs` (status log). Public read access only; all writes server-side.
3. Seed the schema with an accurate real snapshot in the migration so the first render is correct even before the first sync.
4. Ingestion job at `/api/public/sync-visa-data`: shared-secret protected, calls the provider per nationality with rate limiting, upserts `visa_rules`, then recomputes destination counts, global rank, regional rank and the delta versus the previous snapshot.
5. Weekly schedule that calls the job, plus a manual "sync now" path for me to trigger during setup.
6. Rewire the frontend: explorer, rankings, compare and trajectory read from the database via loaders/queries instead of `src/data/passports.ts`. Historical rank series comes from `passport_snapshots`; until enough weeks accumulate it shows the seeded history.
7. Show sync freshness in the UI and keep a graceful fallback to the last good snapshot if a sync fails.

## Technical notes

- Provider calls live in a server function / server route only; the API key is read inside the handler.
- The full matrix is ~199 × 199 rows (~40k) — small for Postgres, fetched per nationality and cached client-side by country.
- An adapter module normalises the provider payload into our four access kinds (visa-free, visa on arrival, eTA, visa required), so swapping providers later touches one file.
- `src/data/passports.ts` is reduced to static country metadata (ISO, name, region, cover colour) after the cutover.
